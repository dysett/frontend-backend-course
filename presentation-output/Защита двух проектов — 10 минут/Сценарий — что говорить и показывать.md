## 4. Маршрут Postman

R01–R05: health, создание, чтение, PUT, PATCH. R06–R08: выдача единственного экземпляра, отказ второму читателю, запрет удаления. R09–R11: возврат, удаление, 404. R12: 400 на неверный фонд. T01–T06: завершение старого Postman-сеанса, 401 без входа, CSRF-сеанс, вход, 403 на неверный CSRF, выход.

Каждый запрос выполняйте ровно в указанном порядке. Коллекция генерирует ISBN и переносит ID автоматически. Можно заранее провести полный прогон и затем повторить с R01: тестовая книжка удаляется. Если вы прервали показ до R10, запись может остаться. T01 касается только cookie jar Postman, а не окна браузера.

Для подготовки результатов тестов заранее выполните npm test в каждой папке и сохраните итоговый вывод. На защите показывайте итог, а не ожидание запуска тестовой MongoDB. Браузерные тесты второго проекта запускаются командой npm run test:ui.

## Короткие ответы на вопросы

### Почему два проекта?

«Товстий клієнт» создан как отдельная переработка предыдущей работы. Код основы скопирован, но каждое приложение имеет свой Express, зависимости, порт и demo-базу. Второе приложение не вызывает сервер первого.

### Где реализован DAO?

В src/dao/book-dao.js. BookDAO владеет коллекцией books и вызывает find, insertOne, findOneAndUpdate, findOneAndDelete и aggregate. Контроллеры работают через BookService.

### Чем PUT отличается от PATCH именно здесь?

Контроллер передаёт в BookService.update признак req.method === "PATCH". bookInput требует все шесть полей для PUT и разрешает непустой набор отдельных полей для PATCH. ID, временные метки, loans и доступность не входят в редактируемые поля.

### Зачем атомарный запрос?

Проверять доступность отдельным чтением и затем писать выдачу опасно при двух одновременных запросах. В addLoan проверка $expr и $push входят в одну атомарную операцию над документом. Отдельный интеграционный тест посылает десять конкурентных запросов на один экземпляр.

### Где выдачи в MongoDB?

В массиве loans внутри документа книжки. Отдельной коллекции loans здесь нет. admins и sessions существуют только во втором проекте.

### Это AJAX или WebSocket?

AJAX на fetch с polling. Следующий опрос начинается через две секунды после завершения предыдущего. WebSocket, SSE и серверная рассылка событий не реализованы. Фоновая вкладка может опрашиваться реже из-за браузера.

### Где фильтрация?

В первом проекте интерфейс отправляет параметры q и available, а BookDAO фильтрует в MongoDB. Во втором Catalog получает список и фильтрует/сортирует его в браузере через useMemo. Сервер второго также сохранил API-фильтры для Postman.

### React Router используется?

Нет. Express отдаёт одну HTML-оболочку для / и /admin. App проверяет window.location.pathname и выбирает Catalog либо Admin. Навигация ссылками загружает страницу, фоновое обновление каталога выполняется без такой навигации.

### Пароль зашифрован?

Пароль хешируется функцией scrypt с индивидуальной случайной солью. При входе сервер вычисляет хеш введённого пароля и сравнивает его с сохранённым через timingSafeEqual. Исходный пароль из хеша не восстанавливается.

### Зачем CSRF, если есть cookie?

Браузер автоматически отправляет cookie. CSRF-токен дополнительно подтверждает, что изменяющий запрос содержит случайное значение из нашего сеанса. Сервер проверяет его вместе с ролью, Origin/Host и SameSite-cookie.

### TTL удаляет сеанс точно через 30 минут?

Очистка MongoDB по TTL не обязана происходить мгновенно. Дополнительно middleware проверяет authenticatedAt и завершает авторизацию при достижении абсолютных 30 минут. Это проверка допуска к запросам, независимая от фоновой очистки.

### Первый API и API с сеансами строго stateless?

Первый API не хранит пользовательский сеанс. Во втором по условию добавлена stateful-авторизация через серверный сеанс. Ресурсные адреса, JSON и семантика CRUD-методов сохранены. Поэтому всю вторую систему не следует называть полностью stateless.

### MongoDB настоящая или массив в памяти?

Это настоящий процесс mongod, запускаемый mongodb-memory-server. В demo указан dbPath и движок WiredTiger, поэтому данные на диске сохраняются между запусками. Тесты используют отдельные временные базы.

### Есть ли ограничения?

Каталог загружается целиком без серверной пагинации. Лимиты запросов рассчитаны на один процесс Express. Нет регистрации читателей, восстановления пароля, MFA и истории возвращённых выдач. Локальный demo использует HTTP и публичный учебный пароль.

## Что формулировать точно

- У первого проекта уже есть интерфейс на обычном JavaScript. Отличие второго не сводится к самому наличию браузерной страницы.
- AJAX во втором проекте реализован polling через fetch. Две секунды — пауза после завершения предыдущего цикла, а не обещание мгновенного обновления.
- Cookie содержит подписанный ID сеанса. Пользователь и роль хранятся на сервере. JWT и хранение авторизации в localStorage не используются.
- Secure включается в HTTPS-конфигурации. В локальном demo по HTTP этот флаг выключен.
- Пароли хешируются, а не шифруются. Клиентская валидация дополняет серверную.
- MongoDB использует официальный драйвер mongodb. Mongoose в проектах нет.
- Строгую stateless-модель нельзя приписывать авторизационной части второго проекта с серверными сеансами.
- В первом проекте API не защищён входом. Во втором права проверяет сервер перед изменением данных.
