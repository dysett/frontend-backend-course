# Реалізація вправи RESTful-сервіс

Сервіс моделює невелику бібліотеку: книжка описує видання та кількість примірників, а активна видача пов’язує один примірник із читачем до визначеного строку. CRUD керує каталогом. Видачі, повернення, перевірка фонду та виявлення прострочень становлять додаткову бізнес-логіку.

## Відповідність завданню

| Вимога | Реалізація |
| --- | --- |
| Зберігання інформаційних одиниць у БД | MongoDB, колекція `books` |
| Отримання всіх записів | `GET /api/books` |
| Отримання запису за ID | `GET /api/books/:id` |
| Додавання | `POST /api/books` |
| Оновлення | `PUT /api/books/:id`, додатково `PATCH` |
| Видалення | `DELETE /api/books/:id` |
| Принцип DAO | `src/dao/book-dao.js`, клас `BookDAO` |
| REST і JSON | URI ресурсів, HTTP-методи, JSON-відповіді, статуси та `Location` |
| Перевірка у Postman | Імпортована колекція з 29 послідовними запитами й перевірками |
| Бізнес-логіка понад CRUD | Видачі та повернення, контроль фонду, прострочення, статистика |
| Node.js та Express | Node.js 22.12+, Express 5 |

## Розподіл відповідальності

`Router` зіставляє URI й метод із контролером. `Controller` читає HTTP-параметри та формує JSON, HTTP-статус і `Location`. `BookService` перевіряє вхідні дані, визначає бізнес-помилки та формує представлення книжок і видач. `BookDAO` виконує пошук, створення, оновлення, видалення й агрегації в MongoDB. Інфраструктурний модуль `db.js` створює спільне підключення й індекс; health перевіряє доступність цієї інфраструктури.

Бізнес-запити до MongoDB зосереджені в DAO. Заміна джерела даних потребуватиме іншої реалізації DAO зі збереженням контракту для сервісу. Драйвер MongoDB використано без Mongoose: обидва способи доступу до MongoDB представлені в наданих навчальних прикладах, а вимога вправи допускає цей вибір. Вхідна модель перевіряється в `validation.js`, вихідне JSON-представлення формується в сервісному шарі.

## Модель даних

Один документ `books` має поля:

```javascript
{
  _id: ObjectId,
  title: String,
  author: String,
  isbn: String,
  publicationYear: Number,
  genre: String,
  totalCopies: Number,
  loans: [{
    id: String,          // UUID v4
    readerId: String,
    borrowedAt: Date,
    dueAt: Date
  }],
  createdAt: Date,
  updatedAt: Date
}
```

`loans` містить тільки активні видачі. Вкладення дозволяє змінити стан видачі та перевірити фонд однією атомарною операцією над документом. Кількість активних видач обмежено кількістю примірників — щонайбільше 100. Повернення вилучає активну видачу; довготривала історія видач у цій навчальній моделі відсутня.

API відображає `_id` як рядок `id`. Поля `borrowedCopies = loans.length` та `availableCopies = totalCopies - loans.length` обчислюються з поточного документа. Окремий змінний лічильник доступності не зберігається. Через це його неможливо випадково збільшити повторним поверненням.

Для `isbn` створено унікальний індекс. Спочатку сервіс нормалізує ISBN і перевіряє контрольну цифру, а індекс не дозволяє створити дублікат навіть одночасними запитами.

## Атомарні бізнес-правила

Для видачі `findOneAndUpdate` одночасно перевіряє, що кількість активних видач менша за фонд і цей читач ще не має примірника книжки, а потім додає видачу через `$push`. Попереднього читання для дозволу операції немає. Додаткове читання після невдалої зміни лише допомагає визначити текст помилки.

Для оновлення фонду DAO додає умову `loans.length <= newTotalCopies` до тієї самої операції, яка змінює документ. Для видалення книжки критерій містить порожній масив видач. Для повернення критерієм є ID конкретної активної видачі; `$pull` вилучає її один раз. Ці умови зберігають фонд коректним під час одночасних запитів.

Усі підтверджені записи використовують `writeConcern: { w: 1, j: true }`: MongoDB підтверджує їх після журналювання. Це також дозволяє відновити останні записи після зупинки локального Windows-процесу. Тест перезапуску перевіряє цей сценарій на WiredTiger.

Офіційна документація описує атомарні складені операції [MongoDB Node.js Driver](https://www.mongodb.com/docs/drivers/node/current/crud/compound-operations/).

## REST і представлення

Книжки мають URI `/api/books/:id`. Активні видачі — підресурси `/api/books/:id/loans/:loanId`. Дія задається HTTP-методом. `GET` читає дані, `POST` створює, `PUT` передає весь набір редагованих полів книжки, `PATCH` — окремі зміни, `DELETE` вилучає конкретний ресурс. Повернення книжки вилучає активну видачу, тому використано `DELETE` її URI.

ID, часові позначки й видачі керуються сервером та зберігаються під час `PUT` метаданих книжки. Відсутній ресурс повертає 404. Створення повертає 201 і `Location`, який можна відразу відкрити через GET. Видалення повертає 200 з JSON-підтвердженням. Повторне видалення дає 404; стан бази після нього не змінюється.

Успішні відповіді й помилки API мають `Content-Type: application/json`. Сервер не використовує сесії клієнтів: потрібні ID та дані містяться в кожному запиті. `Cache-Control: no-store` явно забороняє кешування, щоб клієнт щоразу отримував актуальний стан фонду. Контролери, сервіс і DAO утворюють окремі шари одного застосунку.

Додатковий браузерний клієнт відкривається за `/`. Його файли розташовані в `public/`, а описи ресурсів API — за `/api`. Клієнт використовує `fetch` для тих самих JSON-маршрутів, що й Postman. Форми виконують CRUD і видачу, список активних видач дозволяє повернути примірник. Сервер залишається джерелом бізнес-правил. Після зміни клієнт перечитує дані, а блок останнього запиту показує реальний метод, URI, тіло, статус і відповідь.

Для ознайомлення з принципами й URI використано надану лекцію про REST і [REST API Tutorial](https://restfulapi.net/), зокрема [іменування ресурсів](https://restfulapi.net/resource-naming/) та [HTTP-методи](https://restfulapi.net/http-methods/). Приклади з навчальних файлів адаптовано до актуального API драйвера та `async/await`.

## Перевірка вхідних даних

Клієнт передає дані в JSON-тілі; заголовок `Content-Type` перевіряється сервером. Дозволені поля й типи задаються явно. DAO сам формує критерії й оператори MongoDB; клієнтські об’єкти не використовуються як готові запити до БД. Значення пошуку екранується перед створенням регулярного виразу, тому `.*` шукається буквально.

## Демонстрація на захисті

1. Виконати `npm run demo`, відкрити `/api/health` і `/api/books`.
2. Показати `BookDAO`, `BookService` і контролер як окремі шари.
3. Імпортувати колекцію й оточення Postman та запустити всі запити.
4. Показати конфлікти: повторний ISBN, повторна видача читачу, відсутність примірників і видалення книжки з активними видачами.
5. Повернути примірники, перевірити доступність, видалити тестову книжку.
6. Запустити `npm test`: серед перевірок є одночасні запити та перезапуск бази.
